## 1. 背景と課題

### 1.1 背景

学校の現行出席管理システムでは、教員が授業の開始前後の一定時間内に学生に「出席コード」を提示する必要があります。学生はそのコードを既存の出席管理システムに入力して出席登録を行います。出席コードは既存システムが生成するものであり、教員がシステムから取得して手動で学生に提示します。

### 1.2 現状の課題

現在、各教員はPowerPointスライド・テキストファイル・手書きの板書などそれぞれの方法で出席コードを提示しており、以下の問題が生じています：

- **提示方法の分散**：統一されたツールがなく、各教員が個別に対応しているため、作業の重複が多い。
- **提示忘れ・タイミングのずれ**：授業開始時に出席コードの提示を忘れたり、提示タイミングが正しい受付時間内でないことがある。
- **自動通知機能の欠如**：現行の方法では、授業時間割に基づいて出席コードを提示すべきタイミングを自動的に教員に通知する手段がない。
- **画面投影の不便さ**：通常のウィンドウは他のウィンドウに隠れやすく、コードの文字が小さくて見づらく、投影時の視認性が低い。

### 1.3 解決策の概要

**軽量デスクトップツール**を開発し、出席コードのタイムリーな表示に特化します。本ツールは学期時間割に基づいて現在いずれかの授業の出席コード表示ウィンドウ期間内にあるかどうかを自動判定し、該当する場合には小型の最前面表示ウィンドウを表示します。教員はそこに出席コードを貼り付けて学生に提示します。

## 2. 機能範囲

### 2.1 対象範囲（In Scope）

| 機能カテゴリ | 詳細内容 |
|------------|---------|
| 時間割導出 | 全学共通の学期時間割と各日の固定時限表に基づき、各授業の実施日（第1回、第2回…）を導出する |
| 個人設定 | 教員が「曜日・時限 → 授業名」の形式で個人の授業情報を入力し、個人設定ファイルとして保存する |
| 自動表示 | 授業開始前後の指定時間内において、現在表示すべき授業を自動判定し、出席コード表示ウィンドウをポップアップ表示する |
| 表示ウィンドウ | 小サイズ・ドラッグ可能・常に最前面表示の出席コード表示ウィンドウ（画面投影に対応） |
| 出席コード管理 | 出席コードは既存の出席管理システムから教員が手動取得して貼り付ける方式と、本ツールが直接生成（ランダム4桁数字）して教員が既存システムに手動入力する方式の両方に対応。本ツールは表示のみを担当し、既存システムとの自動連携は行わない |
| 授業調整 | 教員が授業日・時限の設定を確認・変更し、休講・補講・振替などに対応できる |

### 2.2 対象外範囲（Out of Scope）

| 対象外項目 | 説明 |
|-----------|------|
| 学生側機能 | 学生の本人確認・出席登録・提出記録・集計レポートなどは対象外（既存システムが担当） |
| システム連携 | 学校既存の出席管理システムとのAPI連携なし。出席コードの自動取得・出席データの自動送信なし |
| 特殊時間割 | 今フェーズでは集中講義などの特殊な時間割形態には非対応。通常の週単位時間割のみ対応 |
| ネットワーク機能 | ネットワーク不要で動作し、クラウド同期・リモート設定は行わない |

## 3. ユーザーと利用シナリオ

### 3.1 ユーザーの役割

本ツールの主要ユーザーは**教員のみ**です。教員はツールの設定者であると同時に、運用時の操作者でもあります。

### 3.2 主要利用シナリオ（7つ）

以下の7つのシナリオが本ツールの完全な利用ライフサイクルを構成します：

**シナリオ1：学期共通設定のインポート**

- タイミング：学期開始前、または学校が新学期の時間割を発行した後
- 操作：教員が全学共通の「学期時間割ファイル」（各曜日の実際の授業実施日一覧を含む）と「各日時限表」をインポートまたは設定する
- 備考：この設定は通常、学校が提供するテンプレートを流用できるため、多くの学期でゼロから作成する必要はない

**シナリオ2：個人授業設定の登録**

- タイミング：学期開始前、または新しい授業を担当し始めるとき
- 操作：教員がツールに個人の授業スケジュール（例：「月曜2限：授業A、水曜3限：授業B」）を入力し、個人設定ファイルとして保存する
- 備考：ツールはこの設定と学期時間割をもとに、各授業の具体的な実施日一覧を自動導出する

**シナリオ3：授業当日のツール起動**

- タイミング：授業前、通常は教室に到着したとき
- 操作：教員がツールを起動すると、ツールは自動的に個人設定を読み込み、監視状態に入る

**シナリオ4：ウィンドウ期間中の出席コードウィンドウ自動表示**

- タイミング：授業開始10分前〜授業開始後30分（表示ウィンドウ期間内）
- 操作：ツールが現在時刻を自動検知し、該当する授業を特定して、対応する出席コード表示ウィンドウをポップアップ表示する
- 備考：教員が手動操作する必要はなく、自動でトリガーされる

**シナリオ5：出席コードの入力と学生への提示**

- タイミング：出席コードウィンドウがポップアップ表示された後
- 操作：教員が出席コードをツールのウィンドウに入力または貼り付ける。ツールは大きなフォント・高コントラストでコードを表示する
- 備考：ウィンドウは常に最前面表示・ドラッグ可能で、投影画面に継続的に表示される
- **一時コードの動作**：表示ウィンドウの右クリックメニュー「入力」から入力されたコードは**一時コード**であり、以下の特性を持つ：
  - 入力後 **30分** の有効期限（TTL）があり、期限切れ後は自動消去される
  - 設定ファイル（`teacher_config.json`）には**書き込まれない**（メモリ内のみに保存）
  - 最優先（設定ファイルに保存済みのコードを上書き）
  - 設定変更不要な一時的・特例的な状況に適している
- **恒久コード**：設定画面の「スケジュールプレビュー」タブで編集したコードは設定ファイルに保存され、セッションをまたいで有効

**シナリオ6：ウィンドウ期間終了後の待機状態移行**

- タイミング：授業開始後30分を超えたとき（表示ウィンドウ期間終了後）
- 操作：ツールは自動的に表示ウィンドウを非表示にし、待機状態またはバックグラウンド状態に移行する（具体的な動作は設定可能）

**シナリオ7：休講・補講・振替の処理**

- タイミング：出張・病欠・その他の理由で教員が授業スケジュールを変更する必要があるとき
- 操作：教員がツールの設定画面で授業カレンダープレビューを確認し、特定の日付に対して休講・補講・振替操作を実行して保存する
- 備考：調整は本ツールの表示ロジックのみに影響し、学校公式の時間割には影響しない。調整後、ツールの表示動作は即座に調整結果に従う

## 4. データモデル

本ツールのデータは3層で構成されます：**全学共通設定（SchoolConfig）**、**教員個人設定（TeacherConfig）**、**実行時状態（Runtime State）**。

### 4.1 第1層：全学共通設定（SchoolConfig）

この層の設定は学校レベルで決定され、通常は1学期に1回メンテナンスされ、全教員が共用します。

#### 4.1.1 学期時間割

| フィールド | 型 | 説明 |
|-----------|-----|------|
| 学期名 | 文字列 | 例：「2026年度春学期」 |
| 学期開始日 | 日付 | 例：2026-04-01 |
| 学期終了日 | 日付 | 例：2026-07-31 |
| 曜日別授業実施日一覧 | 曜日ごとに分類された日付配列 | 下記参照 |

**授業実施日一覧の核心要件**：

祝日・学校行事日・休講日などの影響により、実際の授業実施日は「毎週」の規則性で単純に導出することができません。そのため、時間割には各曜日に対応するすべての実際の授業実施日を**列挙形式**で明示する必要があります。例：

```
月曜授業実施日：[2026-04-06, 2026-04-13, 2026-04-27, ..., 2026-07-20]  （計14回）
火曜授業実施日：[2026-04-07, 2026-04-14, 2026-04-21, ..., 2026-07-21]  （計14回）
...
金曜授業実施日：[2026-04-10, 2026-04-17, ..., 2026-07-24]
```

この一覧は「各授業の第N回がどの日付に対応するか」を導出するための基礎データです。

#### 4.1.2 各日時限表（Periods）

全学共通で1日あたり固定6コマ（1限〜6限）とし、各時限の開始・終了時刻は以下の通りです：

| 時限 | 開始時刻 | 終了時刻 |
|------|--------|--------|
| 1限 | 08:50 | 10:30 |
| 2限 | 10:40 | 12:20 |
| 3限 | 13:10 | 14:50 |
| 4限 | 15:00 | 16:40 |
| 5限 | 16:50 | 18:30 |
| 6限 | 18:40 | 20:20 |

備考：時限表は全学共通であり、通常は学期を通じて変更されません。

### 4.2 第2層：教員個人設定（TeacherConfig）

各教員が自分の個人設定ファイルを管理します。内容は以下の通りです：

#### 4.2.1 授業一覧

各授業には以下の情報を記録します：

| フィールド | 型 | 説明 |
|-----------|-----|------|
| **授業固有ID** | 文字列 | システムの主要識別子（例：`EEE1000411`）。調整記録（Override）や出席コード保存（キー形式 `{course_id}_{session_key}`）との紐付けに使用。同一教員の設定ファイル内で重複不可 |
| 授業名 | 文字列 | 例：「コンピュータ概論」「データ構造」。表示ウィンドウに使用 |
| 授業コード | 文字列（任意） | 学校公式の授業コード。記録のみに使用 |
| 曜日 | 文字列 | "Monday"/"Tuesday"/"Wednesday"/"Thursday"/"Friday" |
| 時限 | 整数（1〜6） | 時限表のコマ番号に対応 |

例：

```
授業A：月曜 2限
授業B：水曜 3限
授業C：金曜 1限
```

#### 4.2.2 例外調整記録（Overrides）

教員は個別の授業日に対する調整を記録できます。各調整記録には以下が含まれます：

| 調整タイプ | 必須フィールド | 説明 |
|-----------|------------|------|
| 休講（Skip） | 授業名、元の授業日 | その日付を授業なしとしてマーク |
| 補講（Makeup） | 授業名、補講日、補講時限 | 新たな授業実施日を追加 |
| 振替（Reschedule） | 授業名、元の授業日、新しい授業日、新しい時限 | 特定の授業を元の日時から新しい日時に変更 |

すべての調整記録は授業一覧と同一の個人設定ファイルに保存し、手動編集可能な平文（JSON）形式とします。

#### 4.2.3 出席コード（Attendance Codes）

各教員の設定ファイルには出席コード辞書が保存されます。形式は以下の通りです：

```
キー：{course_id}_{session_key}   （例："EEE1000411_03"）
値　：4桁数字の文字列              （例："7231"）
```

| フィールド | 型 | 説明 |
|-----------|-----|------|
| キー名 | 文字列 | `{授業固有ID}_{回次番号（2桁ゼロ埋め）}`、特定の授業の特定の回を一意に識別 |
| キー値 | 文字列 | 4桁数字の出席コード（0000〜9999）。教員が手動入力またはランダム生成機能で一括生成 |

備考：
- 出席コード辞書は設定ファイルとともに永続保存され、セッションをまたいで有効
- 表示ウィンドウの「入力」メニューから入力した**一時コード**はこの辞書には書き込まれない（メモリ内のみに保存、TTL30分）。一時コードはこの辞書のコードより優先される
- 出席コードを永続的に保存するには、設定画面の「スケジュールプレビュー」タブで変更するか、JSONファイルを直接編集する

### 4.3 第3層：実行時状態（Runtime State）

実行時状態は永続化されない（または一部のみ永続化）、プログラム実行中に動的に管理されます：

| 状態項目 | 説明 |
|---------|------|
| 現在の日時 | システム時刻をリアルタイムで取得 |
| 現在ヒットしている授業 | 時刻に基づき、現在どの授業の表示ウィンドウ期間内にあるかを判定（存在しない場合もある） |
| 現在の出席コードテキスト | 教員が今回のウィンドウ期間内に入力・貼り付けた出席コード |
| ウィンドウ位置 | ユーザーがドラッグした後のウィンドウ座標。次回起動時に復元（永続化） |
| ウィンドウ表示・非表示状態 | 現在、表示ウィンドウが可視状態かどうか |

## 5. 主要業務ルール

### 5.1 授業実施日の導出ルール

**入力**：
- SchoolConfig 内の特定曜日の授業実施日一覧
- TeacherConfig 内の特定授業に対応する曜日と時限

**出力**：
- その授業の「授業実施日一覧」を時系列順に並べ、第1回・第2回…と番号付けしたもの
- 逆引き対応：特定の日付を指定して対応する回次を返す（その日にその授業がある場合）

**ルール説明**：

1. SchoolConfig から該当授業の曜日に対応する授業実施日一覧を取得する。
2. その日付一覧を昇順に並べ、該当授業の基本授業日シーケンスとする。
3. 例外調整を適用する前は、第N番目の日付がその授業の「第N回」（基本回次）となる。
4. 例外調整を適用した後は、第5.6節のルールに従って実際の授業回次を再確定する（「調整が回次番号に与える影響」参照）。

**制約**：今フェーズでは通常の週単位時間割のみ対応。集中講義などの特殊な時間割は非対応。

### 5.2 表示ウィンドウルール

各授業の各授業日に対して、表示ウィンドウは以下のように定義されます：

```
授業開始時刻 = その授業日に対応する時限の開始時刻（時限表より）

表示ウィンドウ開始 = 授業開始時刻 − pre_class_minutes（デフォルト10分）
表示ウィンドウ終了 = 授業開始時刻 + post_class_minutes（デフォルト30分）
```

> **パラメータ説明**：`pre_class_minutes` と `post_class_minutes` は設定可能なパラメータで、`teacher_config.json` の `settings` フィールドに保存されます（第4節データモデル参照）。デフォルト値はそれぞれ10分と30分であり、教員が必要に応じて変更できます。

**判定ロジック**：

- システムの現在時刻がある授業の表示ウィンドウ内に入ったとき（`ウィンドウ開始 ≤ 現在時刻 ≤ ウィンドウ終了`）、その授業が「ヒット」し、ツールは該当授業の出席コード表示ウィンドウを表示します。
- 時刻チェックはポーリング方式で継続的に行います（推奨頻度：30秒または1分ごと）。時間の境界を越えるタイミングに対応するためです。

**例**：

教員の授業が水曜3限（13:10開始）に設定されている場合、その水曜日の表示ウィンドウは以下の通りです：

```
ウィンドウ開始：13:00（13:10 − 10分）
ウィンドウ終了：13:40（13:10 + 30分）
```

つまり、授業がある水曜日にシステム時刻が13:00〜13:40の間にある場合、ツールは自動的にその授業の出席コードウィンドウを表示します。

### 5.3 複数授業の競合処理

通常、同一時刻に複数の授業が同時にヒットすることはありません（同じ時限に2つの授業を同時に担当することはできないため）。ただし、教員の設定に誤りがある場合（例：同じ時限に2つの授業が設定されている）、システムは以下のルールに従って確定的に1つの授業を選択して表示します：

**優先度ルール**（優先度の高い順）：

1. 「表示ウィンドウ開始時刻と現在時刻の差の絶対値が最小」の授業を優先表示する（ウィンドウ開始時刻が現在時刻に最も近い授業）。
2. それでも同値の場合、時限番号の小さい授業を優先する（例：2限 > 3限）。

このルールにより、表示内容が不確定にならないようにします。

### 5.4 ウィンドウ期間外の動作

システムの現在時刻がいずれの授業の表示ウィンドウ内にもない場合：

- **デフォルト動作**：ツールは出席コード表示ウィンドウを非表示にし、待機状態に移行します（システムトレイアイコンは表示継続）。
- **手動オーバーライド（任意）**：トレイアイコンまたはメニューから教員が手動で表示ウィンドウを開けるようにします（時間割外の臨時説明などに対応）。
- 待機状態でも、ツールはバックグラウンドで動作を継続し、次のウィンドウ期間が来た際に自動的にポップアップ表示できるよう時刻を監視し続けます。

### 5.5 出席コード入力ルール

- 出席コードは教員が学校既存の出席管理システムから手動取得し、本ツールの表示ウィンドウに入力または貼り付けます。
- 本ツールは出席コードの形式や有効性を**検証しない**、いかなるデータも**送信しない**、表示のみを担当します。
- 出席コードのテキストボックスは直接貼り付け操作をサポートし、ワンクリックで消去できる機能（任意）を提供します。
- 出席コード表示後は、目立つ形式（大きなフォント・高コントラスト）で表示し、投影画面で学生が認識できるようにします。

### 5.6 授業調整ルール

#### 5.6.1 休講（Skip）

- **トリガー条件**：教員が特定の授業の特定の授業日を「休講」としてマークする。
- **表示動作**：その日付では表示ウィンドウが起動しない。システム時刻が元のウィンドウ期間内に入っても表示ウィンドウはポップアップしない。
- **即時反映**：休講マークが表示ウィンドウ期間開始後に入力された場合、ツールは直ちに表示ウィンドウを非表示にして待機状態に移行します。

#### 5.6.2 補講（Makeup）

- **トリガー条件**：教員が特定の授業に通常外の授業日と対応する時限を追加する。
- **表示動作**：補講日の表示ウィンドウ期間内（補講時限開始10分前〜開始後30分）に、ツールはその授業の表示ウィンドウを自動起動します。
- **補講時限の範囲**：1限〜6限のいずれも指定可能。

#### 5.6.3 振替（Reschedule）

- **定義**：特定の授業を「元の日付＋元の時限」から「新しい日付＋新しい時限」に変更する。
- **等価な意味**：振替はロジック上、「元の日付を休講にする＋新しい日付を補講にする」と同等です。
- **画面表示**：単一の操作として提示します（2ステップ操作ではなく）。教員が理解しやすく、操作を振り返りやすくするためです。
- **元の時限の処理**：元の時限は振替記録の中でどの授業回が変更されたかを識別するために使用され、新しい時限が新しいウィンドウ期間の算出基準となります。

#### 5.6.4 調整が回次番号に与える影響

調整操作は授業の「実際の授業回次」番号に影響します。ルールは以下の通りです：

- 回次番号は**実際の授業実施順序**に従い、全ての休講・補講・振替調整を適用した後、実際に実施された授業日を時系列昇順で並べ直して番号を振ります。
- 具体的なロジック：
  1. 基本授業日一覧を取得する（SchoolConfig 内の該当曜日の日付シーケンス）。
  2. 休講としてマークされたすべての日付を除外する。
  3. 振替の元の日付を新しい日付に置き換える（該当位置から元の日付を削除し、新しい日付を追加）。
  4. 補講のすべての日付を追加する。
  5. 上記のマージされた日付セットを昇順に並べ、第1回・第2回…と順番に番号を振る。
- ツールは回次プレビュー機能を提供し、調整後の各回次が正しい日付に対応しているかを教員が確認できるようにします。

> **現状の実装について**：実際の使用では、振替（Reschedule）が最も一般的な調整タイプです（`teacher_config.json` の実例を参照。全調整記録が `reschedule` タイプであり、休講・補講の記録はありません）。また、UIは振替記録の追加エントリ（`RescheduleDialog`）のみを提供しています。休講（Skip）と補講（Makeup）は現在、JSONファイルを直接編集して入力する必要があり、グラフィカルな操作画面はありません。

## 7. 画面要件

### 7.1 出席コード表示小ウィンドウ（コア画面）

本ツールのコアとなるインタラクション画面であり、授業ウィンドウ期間中に教員と学生の両方から見える状態になります。

**レイアウトとスタイル要件**：

- 全体サイズは小さくする（推奨：画面幅の25%以下）。画面の小さな一角のみを占有する
- 出席コードのテキストは超大フォント（推奨：48pt以上）を使用し、高コントラスト配色（白背景・黒文字または黒背景・白文字）とする
- 現在の授業の基本情報を表示：授業名、今日が第何回か（現状の実装では日付は表示しない）
- 複雑なコントロールは含めない。インターフェースは極めてシンプルに保ち、視覚的なノイズを最小化する

**インタラクション要件**：

- 常に最前面表示で、他のウィンドウに隠れない
- マウスで任意の場所にドラッグでき、位置は記憶されて再起動後に復元される
- 入力フォーカスを奪わない（教員が他のソフトウェアを使用する際に支障をきたさない）
- 出席コードの入力欄（入力・貼り付け可能）と消去ボタンを提供する

### 7.2 設定画面（授業前に使用）

この画面は授業前の設定フェーズにのみ使用されます。極シンプルである必要はなく、ある程度複雑でも構いません。

**基本設定エリア**：

- 現在使用中の全学共通設定ファイルのパスを表示し、読み込みに対応する
- 授業一覧の操作フォームを提供：授業の追加・授業名/曜日/時限の編集・授業の削除
- 衝突検出ボタンを提供し、現在の授業設定に時間の重複がないかチェックする

**授業カレンダープレビューエリア**：

- 特定の授業を選択すると、その授業の第1回〜第N回の日付一覧を表示する
- 調整がある日付（休講・補講・振替）をマークし、調整後の実際の回次配列を示す
- 特定の日付をクリックして調整操作ができる

**調整記録管理エリア**：

- すべての既存調整記録（タイプ・授業・元の日付・新しい日付など）をリスト形式で表示する
- 新しい調整を追加できる（タイプを選択して対応フィールドを入力）
- 特定の調整記録を削除できる
- 「調整は本ツールの表示ロジックのみに影響し、学校公式の時間割には影響しない」ことを明確に案内する

### 7.3 システムトレイ

- ツール起動後、システムトレイにアイコンを表示する
- トレイアイコンにはメニューを提供：設定画面を開く・表示ウィンドウの手動表示/非表示（任意）・終了
- 表示ウィンドウを閉じた場合、ツールはトレイ待機状態に移行し、直接終了しない

## 8. 技術要件

### 8.1 プログラミング言語とフレームワーク

- **Python** を推奨（開発効率が高く、GUIエコシステムが成熟しており、このような軽量ツールに適している）
  - GUIフレームワーク：**PySide6** または **PyQt6** を第一候補とする（Qtは最前面表示ウィンドウ・ドラッグ可能・システムトレイをネイティブサポート）
- 代替として **C++** も使用可能。同様に **Qt6** フレームワークを採用

### 8.2 クロスプラットフォームサポート

| プラットフォーム | 要件 | 配布形式 |
|--------------|------|---------|
| Windows 10/11 | 必須 | 独立した `.exe`（PyInstaller または Qt デプロイツールでパッケージング） |
| macOS（直近3バージョン） | 必須 | 独立した `.app` アプリケーションバンドル |

- プラットフォーム固有のAPIに依存しないこと。すべてのGUI操作・ファイル操作はクロスプラットフォームなインターフェースを使用
- WindowsとmacOSで機能と画面の一貫性を保つ

### 8.3 依存関係と配布

- 最終的にリリースされる実行ファイルは**独立したパッケージ**とし、ユーザーがPythonランタイムや任意のサードパーティライブラリを手動インストールする必要がないようにする
- 設定ファイル形式：**JSON平文**。手動編集に対応し、クロスプラットフォームで移植可能（別のPCに設定ファイルをコピーするだけで使用できる）

### 8.4 パフォーマンスと安定性

- 起動速度が速く、ツールの起動から準備完了まで3秒以内に完了すること
- 時刻ポーリングロジックはシステムのスリープ/ウェイクアップ・クロック調整に対してロバストで、これらの原因でクラッシュやエラーダイアログが発生しないこと
- メモリ使用量が少なく、長時間バックグラウンド動作でメモリが継続増加しないこと

### 8.5 保守性

- 設定ファイルの構造が明確で、フィールド名に意味があり、形式がドキュメント化されていること
- コア業務ロジック（時間割導出・ウィンドウ判定・回次計算）はGUI層から分離し、ユニットテストが容易なこと
- 主要な業務ロジックにはコードコメントを付与すること

## 9. 受入基準

以下の7つの受入基準は第3節の7つの主要利用シナリオに対応しており、すべてを満たした場合に納品合格とします：

| 番号 | 受入項目 | 受入方法 |
|-----|---------|---------|
| AC-01 | 教員が画面上で「曜日・時限 → 授業名」の形式で個人授業を設定し、JSONファイルとして保存できる。再起動後も設定が正しく読み込まれる | 手動テスト |
| AC-02 | ツールが学期時間割をもとに特定の授業の全授業日を正しく導出し、プレビュー画面で回次ごとに表示（第1回・第2回…）でき、期待される日付と一致する | 手動比較 / 自動テスト |
| AC-03 | 授業開始前N分〜開始後M分（N/Mのデフォルトは10/30、設定可能）において、ツールが対応する授業の最前面表示小ウィンドウを自動ポップアップする。ウィンドウ期間外はポップアップしない | 手動テスト（システム時刻調整による補助検証可） |
| AC-04 | 表示小ウィンドウが常に最前面表示（他のウィンドウに隠れない）・マウスドラッグ可能・画面占有面積が小さい。閉じた後も位置が次回起動時に復元される | 手動テスト |
| AC-05 | 教員が小ウィンドウに出席コードを貼り付けられ、出席コードが大きなフォント・高コントラストで表示され、投影画面で明確に認識できる | 手動テスト（実際の投影で検証） |

| AC-07 | 教員が設定画面で授業カレンダープレビューを確認し、特定の日付に対して休講・補講・振替操作を実行できる。操作保存後、ツールの表示ロジックが調整結果に従い機能し、プレビューの回次番号が正しく更新される | 手動テスト / 自動テスト |
